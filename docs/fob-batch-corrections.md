# FOB 批量报价逐项退回与修正

发布候选：`quotation-2026.10.11-02`。用户已授权统一提交和部署，实际发布状态以服务器 manifest 和发布验收证据为准。界面预览使用隔离的 DEMO 数据；测试使用临时 PostgreSQL，未向生产写入报价、采购资料或审核数据。

## 操作流程

1. 管理员在报价详情开始逐项审核，勾选异常商品，为每项填写自定义退回原因。界面明确提供“其余未选的待审核项一并通过”选项；原先已通过项不被这次退回覆盖。
2. 报价员通过审核消息或报价记录的“处理异常项”进入。系统自动带出退回商品、原数量、采购来源及退回原因，不修改普通报价草稿。
3. 重新查询对应采购来源，展示原最终价与重算后最终价。数量可按最新起订量和下单倍数调整；最终价格不可手填。全部阶梯保留阶梯展示方式。
4. 只提交选中的有效项。提交时服务端重新核验采购时间戳、汇率、计算规则及金额；任一提交项失效则该次请求整体不写入。可取消失败项后提交其余有效项。
5. 提交成功项进入待审核，未解决项继续保留退回状态。只要存在待复核项，该记录进入管理员待审核列表。管理员只能通过重新提交后的项。

## 异常与保护

- 区分 SKU 不存在、权限/登录异常、网络/超时、采购资料不完整、运费冲突、数量不合法、资料未变化。
- 资料、数量及计价参数均未变化时保留退回，提示核实采购，不将重新点击查询视为已经修正。
- 查询并发限制为 4；单项可重试，超时有截止。修改数量或财务参数后清除旧查询结果。
- 客户端查询结果不是写入依据。服务端锁定报价记录并验证报价版本及审核版本，防止跨页面覆盖、审核占用冲突及采购资料在查询后再次更新。
- 不确定的提交结果可以用同一个幂等键原样重试；不会重复生成修订。
- 原始 quotation_record.payload 不因修正而覆盖。修订、逐项审核和审计保存在 quotation_review.state；可读取原始版及各次修订。
- 保留未修改商品快照、原报价单列顺序与行顺序。更新发生变化的数量范围及下单倍数说明。
- 逐项审核生效后，客户报价单导出与成交选项仅包含已通过商品。已打开详情发现审核版本更新时，停止导出，要求加载最新记录。
- 用户主动修改报价内容或撤回时，按原有失效流程取消相关通过状态；采购后台更新不会触发历史报价重算。

## 本地验证

- 前端 16 个测试文件、139 项测试通过；TypeScript 检查及 Vite 正式构建通过。
- 临时 PostgreSQL 的真实登录会话验证员工、其他员工、采购、财务及管理员权限；验证退回、部分提交、待审核列表、重复并发提交、采购价格及阶梯边界重算、原始快照不变、跨账号读取一致。
- 后端共 62 项测试通过（FOB PostgreSQL 端到端 9 项、FOB 计算/修正 16 项、普通报价审核 30 项、生命周期 7 项），无跳过。
- 运行中的本地组件预览：`http://127.0.0.1:5192/outputs/fob-corrections/index.html`；截图与演示文件保存在 `outputs/fob-corrections/`。它是实际组件加模拟响应，不代表生产验收。

上线需要同步发布前后端并刷新旧页面。旧前端的整单审核不能处理已进入逐项审核的批量记录；后端会明确阻止覆盖已通过项。

产生修订后，回滚后端必须继续识别 fobRevisionSnapshot 与逐项审核状态；不能退回到只读取原始 payload 的旧实现，以免把旧价格当作最新结果展示。
