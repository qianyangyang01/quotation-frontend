# 网页更新提醒与发布说明

普通更新与关键更新都使用服务端平滑切换；关键更新只增加旧页面的客户端操作门禁，不等于允许重启生产服务或发布不兼容接口。

## 每次发布

1. 修改 `src/data/applicationRelease.json`：唯一 `version`、实际发布日期、简明标题、具体功能、业务入口。只写本次实际发布的功能，不将测试、预览、未启用功能写为已上线。
2. 默认 `policy=optional`，保留当前生产 `requiredEpoch`。旧页面提示但允许完成编辑、保存和上传。
3. 业务规则要求必须更换客户端时设置 `policy=required`，同时将 `requiredEpoch` 改为新的唯一标记。此后所有普通发布沿用这个标记，防止跳过关键版本的页面漏掉强制更新。
4. 从实际活动前端读取 `app-version.json` 保存到发布包，执行 `node scripts/verify-application-release.mjs /绝对路径/生产版本.json`。构建本身也校验说明格式；前置版本检查必须在准备、切换前再次核对实际生产未变。
5. 继续核验接口兼容并使用当前 `buildId` 构建。`releaseBuildId` 每次构建独立生成并嵌入代码，不能以页面启动时读到的远端版本作为自身版本。不得以必更新策略绕过已有兼容性、锁、后台任务或历史报价保护门禁。
6. 运行完整 CI 和隔离演练，包括普通更新跨切换保存、关键更新写请求门禁、已接收请求完成、备份失败不刷新、旧页面资源及回退。发布后只读验收。

## 内容保护与使用

- 检测到更新永不自动刷新，也不自动重发保存。
- 主报价入口沿用当前标签页、当前账号的输入备份，成功回读后才允许手动刷新；它不是历史报价或自动提交。
- 其他入口须用户先保存或复制保留，并再次确认刷新。不能宣称所有页面具备自动恢复。
- 提交或上传期间禁止通过提醒按钮刷新；已提交请求继续完成。关键更新阻止后续新的写请求，但允许只读查询、草稿恢复及已接受分块上传完成。
- 更新提醒不会被“已读”隐藏。进入新版后首次显示本次功能介绍，可关闭；顶部“更新说明”永久保留入口。已读状态按账号、业务版本保存。
- 版本接口暂时失败不冒充更新、不打断正常业务；已确认的关键更新门禁不会因断网或回滚被静默撤销。

## 首次接入

2026-11-23 之前的旧客户端只比较兼容 `buildId`，不认识发布说明和关键标记。首次以普通兼容更新接入；同事需要保存手头内容后手动刷新一次，之后才具备新提醒逻辑。不能通过修改旧版本文件或强制刷新正在编辑的页面绕过此限制。关键不兼容变更仍按维护窗口管理。
