# 页面版本更新与模块联动

## 行为

生产前端每次构建生成唯一 `buildId`，编译进脚本，并输出相同标识的 `app-version.json`。版本文件与入口 HTML 均禁止缓存，带内容哈希的静态资源继续长期缓存。

已打开的页面每 60 秒检查一次版本；隐藏标签暂停轮询，重新可见、切回窗口、恢复联网和切换模块时再次检查。连续的焦点事件去重。新业务写入发送前核验版本，共享进行中的检查及最近 10 秒成功结果，失败后退避 30 秒；手动重试和后台检查可提前恢复。首次核验直接与脚本中的构建标识比较，避免页面刚打开就遇到发布时误把新版本当作旧页面的基线。

发现版本不同后，页面持续显示更新提示并阻止新的业务写入。页面不会自行刷新，用户可以先复制输入备份，已有撤回编辑草稿的保存通道保留。普通新报价仍沿用现有流程，不承诺自动保存输入。点击刷新须确认未保存内容已经处理；刷新保留当前路径、查询参数与锚点，并增加缓存绕过参数。正在进行的提交或上传完成前，提示内的刷新按钮禁用。

## 模块范围

| 模块/操作 | 发现新版本后的行为 |
| --- | --- |
| 普通、组合、手工成本、仅运费报价，以及再次发起、撤回编辑 | 新业务写入在公共 HTTP 层拦截；保存普通草稿仍可用 |
| FOB 报价、FOB 批量、批量单品报价 | 预览/保存等 POST 请求受同一版本检查保护 |
| 审核、报价状态、客户报价修改 | 新提交在公共入口检查版本，已发出的请求照常接收真实结果 |
| 采购与供应商资料、导入确认、财务、权限、模板 | 新增/修改/删除和导入启动检查版本 |
| 物流导入、审核发布、回滚、切库 | 新操作检查版本；既有上传会话的分块及完成可继续，正式审核发布仍须刷新 |
| 采购图片续传与取消 | 已存在导入任务的图片部分及取消可继续；正式确认仍须刷新 |
| 普通报价草稿、登录、退出、修改密码 | 保留恢复和认证通道；原有账号、权限及 CSRF 检查仍生效 |
| 历史报价读取与导出 | 保留已有历史快照，不重算、不改运费/报价/审核/处理/成交状态 |

当前未保存报价的矩阵复制、普通客户报价单、FOB 数量报价/报价单、批量单品及 FOB 批量导出也会在检测到更新后暂停。共享组件以显式 `currentQuote` 来源标识区分新报价和历史记录，不以 `readOnly`、`recordMode` 或 `savedSheet` 猜测历史来源。生成中的图片和 Excel 在输出前复核，复制锁等待结束及 HTML 复制失败后的文本回退前再次检查；已生成的新报价图片撤销预览但保留编辑输入；历史复制、图片及 Excel 导出保持可用。

普通草稿白名单仅限 `/quotation-drafts/mine/state` 的 PUT/DELETE，不能借此提交正式报价。上传白名单仅限已经存在会话的收尾端点，不包括创建会话、业务审核或发布。服务器继续负责会话所有权及业务权限校验。

`POST /quotation-sync/logistics` 为只读资料核验，既不触发版本探测，也不占用提交/上传刷新锁，避免逐 SKU 轮询放大额外请求。

更新检测不会操作 LocalStorage、IndexedDB、数据库、业务缓存或历史记录。已提交请求不会因为随后发现更新而被改报为失败，也不会由更新机制自动重试。取消请求或切换账号发生在版本核验期间时，原提交仍不得发送。

## 资料更新与代码发布的区别

`buildId` 识别前端构建变更，包括更换到不同构建的回滚。后台页面内修改的采购资料、财务参数和物流价格，继续使用项目现有的资料版本、同步与提交校验机制，不靠重载页面来代替业务版本校验。

普通报价已有每 5 秒及焦点/联网恢复时的资料版本轮询，提交前再次核验。本次补齐 FOB 单品、批量及修正入口对 `exchange-rate` 版本的检查：只读取 `/quotation-sync` 的版本信息，发现汇率变化后要求刷新并沿用新报价输出保护；不后台强制水合财务缓存，不改变当前汇率或卸载报价单，以免丢失未保存客户名称、备注、数量和排序。核验失败保持输入并由原同步机制重试，不能把失败当作已确认变更。

**纯后端镜像更新不会改变前端构建标识。** 修改计算代码或接口契约的发布，应联动重新构建并发布前端，使已打开的页面收到更新提示；本功能没有新增后端最低客户端版本接口。前端检查与业务请求之间仍存在网络时序窗口，最终金额、权限、资料版本及历史保护仍以服务端校验为准。

**首次上线仍需要用户刷新一次。** 上线前已经打开的页面没有这段检测代码，不能被新增的浏览器脚本追溯控制。此后每次发布即可自动检测并要求更新后操作。

## 故障与恢复

- 无网络、超时、404、HTML 降级页或不合法版本文件：不认定发生更新，不触发自动刷新；提示后自动重试，健康业务接口仍可正常使用。整个探测（含响应体）最长等待 2 秒，不依赖 fetch 是否响应 abort，迟到结果无状态副作用。
- 已确认新版本后再遇网络失败或服务器回滚：更新提示保持到用户刷新，避免不同模块处于混合状态。
- 回滚到没有版本文件的旧发布：当前带检测的页面会显示无法核验，不因版本文件缺失阻断健康业务，用户也可保留内容后主动刷新进入旧发布，不发生刷新循环。
- 刷新前的确认不等于自动备份。已有撤回编辑草稿沿用原有保存流程；普通新报价、文件选择、FOB/批量尚未保存的输入等仍需用户自行保留。
- 本地开发模式不启用生产版本探测，避免开发服务器没有版本文件时阻止调试。

## 验证入口

- `node --test tests/app-version-build.node.mjs`：实际 Vite 内存构建，核验 manifest/脚本标识一致、再次构建标识改变、开发模式禁用检测。
- `pnpm exec vitest run src/services/appUpdate.test.ts src/services/appUpdateHttp.test.ts src/components/AppUpdateNotice.test.ts src/services/http.test.ts src/services/logisticsResumableUpload.test.ts --maxWorkers=1`：检测与超时、焦点恢复、取消、账号切换、写入隔离、草稿/上传豁免及提示交互。
- `pnpm build`：全项目类型检查与生产构建。

部署验收须检查生产版本文件响应头及实际脚本标识，并使用新旧两个构建验证旧页更新提示。生产验收只查看与预览，不能为验证拦截而创建业务数据。

## 深度验证范围（2026-10-23）

- 故障注入：404/503/HTML、同步异常、不响应 abort 的请求及响应体、迟到错误版本、恢复及退避。
- 并发及时序：100 个并发与 100 个顺序操作复用核验、成功缓存期内的后台核验、单个调用取消、账号切换、已发出业务提交照常完成。
- 模块联动：普通/FOB/批量报价当前输出与历史输出区分、剪贴板锁延迟、HTML 回退、生成中图片与 Excel、财务汇率更新、草稿及上传收尾。
- 交付检查：完整 Vitest 回归、全项目 ESLint、类型检查与生产构建、实际镜像 nginx 启动/清单/资源、精确提交 GitHub CI。
- 发布及回滚证据记录在对应版本发布包中；生产验收只读，不创建测试业务记录，不重算历史报价。
