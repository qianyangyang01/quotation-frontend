## 页面与接口

- 概览三张统计卡片后、业务员排行前新增排行榜；默认 Top 5，展开后每页 20 / 50 条。
- 使用顶部日期、国家、业务员、品类、关键词筛选，初始日期和重置日期均为北京时间近 30 天。
- 原概览日期比较也统一为北京时间，避免 UTC 午夜附近与后台聚合相差一天。
- 单独加载 `GET /api/v1/quotations/channel-ranking`，不等待原概览采购/报价统计完成，也不把新增渠道明细塞进原 analytics-records 响应。
- 请求防抖 300ms，筛选变化取消旧请求、清除旧结果，按代次和账号丢弃迟到响应。无自动轮询。
- 支持分页、导出本页、核查重点弹窗；具有物流权限且匹配当前渠道时，可以定位其物流商。
- 权限沿用 `PERM_allRecords`；未扩大普通员工或纯物流角色的公司报价权限。

## 口径与保护

- 在服务器对「报价记录 ID + 国家 + 渠道身份」去重，不重复计入同单数量档；有效备选渠道计入。
- 优先使用原记录稳定渠道 ID；通过既有 company binding 对应已确认的跨库渠道。没有 ID 时仅使用唯一精确编码/物流商渠道名匹配；有明确但失效 ID 时不会按相似名称猜测。
- 同名不同物流商分开；国家名称/代码做规范化；不明渠道保留使用量并标为待匹配。
- 仅统计 active/archived；排除 withdrawn/trashed、FOB、freight-trial、明确 isTest、不可用或没有正数有效报价的选项。
- 兼容 quoteOptions、specifiedQuotes、早期单渠道主记录；现代空选项数组不虚构主渠道。
- 占比分母使用当前全部业务筛选结果，切换待审视图不改变分母。
- “渠道有待审版本”来自真实物流草稿，是渠道级提示，具体国家是否受影响仍需核对原表。未匹配、历史渠道、待核查分别显示。
- 不将已发布或某条报价审核通过冒充独立线路核查；本次不创建新的核查结论写入流程，因此没有伪造的“已核查”或周期复核时间。
- 新接口只有只读事务和 SELECT 聚合，无保存报价、重新计价或审核状态更新调用，无数据库业务迁移。

## 性能

- 使用现有 lifecycle_state/created_at 索引限制来源范围，数据库完成选项展开、去重、分组，只返回聚合页面。
- 最多并行 2 个排行查询；SQL 超时 6 秒，事务超时 8 秒；超限显示可重试错误，不用零统计替代。
- 复杂 JSON 查询在本次事务内关闭 JIT，避免编译时间大于查询时间。不修改数据库全局参数。
- 10,000 条多渠道报价查询计划：JIT 开启 3350.978ms，其中 JIT 编译约 2201.719ms；关闭后 777.601ms。
- 同一万条数据加国家、业务员、品类和关键词筛选：636.517ms。
- 带 JaCoCo / 集成测试监测的万条记录聚合：1258ms；返回 4 个聚合条目，小于 5KB。
- 真实历史副本 Top 5：4 次完整本地 HTTP 请求为 150 / 118 / 114 / 117ms，响应 2147 bytes。
- 以上是本机共享 Docker 环境实测，不能当作生产延迟保证。未将原概览的全部其他统计接口重新设计。
