# 采购粘贴、审核同步与两端一致性专项测试

2026-09-23。基线为已发布的 `quotation-2026.09.23-23` / `d18e6a1fd5ed9f5d7ec9f48124dc6cad89b25ab4`。隔离 HTTP 压测使用修复提交 `743ac650a2af3663fa63101ffaa134438abce5ef` 的后端，JAR SHA-256 为 `5988fccbbe88174f5323e2b8d71e89adf5027bcec05635d3eb00bfb9345abd0e`。后续草稿兼容修复及浏览器复验为 `61d99375b6447f7f84a8d5079b23b1d2d97c98d2`。本任务未部署生产；已交给首页性能/五角色验收任务统一集成。

## 结论与修复

1. **采购保存成功后的可见性通过。** 真实调用 `/purchase-products/paste`，然后员工与管理员立即按 SKU 搜索；100 行整批逐条核验、同 SKU 重试、50/100 会话同步突发均通过。实际浏览器粘贴 `UIPV26092301`，已打开的员工报价页在满足必填条件后无需刷新即可查到原价 12.34 元、重量 125g。管理员搜索得到相同原始资料；员工计入成本 12.46 元符合现有零票点乘 1.01 规则。
2. **审核接口发现并修复真实版本错误。** 原实现审核历史 `quoteVersion` 使用小整数 LongNode；JSON 回读变为 IntNode，Hibernate 脏检查把未发生语义变化的状态再次写入。PostgreSQL 红测确认 claim 响应版本为 2，事务提交后为 3，直接使用响应调用 complete 得到 409。改为按整数范围写入一致的数字节点；响应版本与提交版本相等，claim→complete 无需重新加载。保留旧版本冲突、独占审核、价格变化重新核对等保护。
3. **员工详情补齐实时审核结论。** 两端共用只读状态展示，操作按钮继续受权限控制。实际双登录浏览器验证：员工保持列表和详情打开，管理员领取后显示审核中，完成后自动显示价格异常；未手动刷新员工页面。删除同页面多余的 15 秒列表轮询，保留已有的 3 秒筛选同步，慢请求不会被第二个计时器重复触发。
4. **补齐不完整旧草稿防护。** 合成 schemaVersion=2 草稿保留 SKU、缺少 product 子对象时，恢复原先抛出 primaryChannelKey 空对象异常。两处可选链修复，红绿回归及浏览器重新打开均通过；不改变采购价格或草稿保存格式。

审核采用请求完成后等待 3 秒的轮询，**不是零延迟推送**。可见标签正常约 0–3 秒看到变更，隐藏标签暂停，回到页面或恢复网络立即核验；网络和服务器响应可增加等待时间。

## 环境、负载与时间

- 独立 Compose 项目 `quotation-sync-stress-20260923`，只绑定 `127.0.0.1:18239`，独立 PostgreSQL `quotation_perf`、Redis、网络；没有使用生产账号或数据。浏览器前端仅用于本机验收，端口 18240。
- 后端 2 CPU / 1280 MiB，JVM 堆 768 MiB；PostgreSQL 2 CPU / 768 MiB；Redis 128 MiB。连接池观测为 10 个应用连接加采样连接。
- 起始合成采购 10,000 条、报价 2,600 条（含 600 条审核夹具）、草稿 60 条。先运行预热/异常验证，再持续新增；不是固定数据量的等条件容量对比。
- 50 个独立账号：30 员工、10 采购、10 管理员；持续混合阶段 240 秒。资源记录北京时间 23:12:59–23:17:10，此阶段另一任务回归运行至 23:16:28，属于共享主机压力证据。
- 100 个独立账号：60 员工、20 采购、20 管理员；持续混合阶段 180 秒。资源记录北京时间 23:17:21–23:20:33，已与另一个任务错开构建和重负载测试。
- 每采购账号每轮粘贴 10 行并立即搜索，停顿 500ms；每管理员反复领取/完成审核并搜索新采购，停顿 350ms；员工每 3 秒轮询 10 条记录并查询审核通过筛选，交替搜索新采购。额外 5 轮所有账号同时搜索刚新增的同一个 SKU，实测峰值在途请求分别达到 50 / 100。
- 是真实认证 HTTP 会话混合压力，**不是同时运行 100 个完整浏览器**。页面行为另由实际双登录浏览器和组件回归验证；轮询可见延迟由相同 3 秒节奏的 HTTP 客户端测量，不能冒充公网端到端渲染时间。

## 两端一致性与联动验证

| 项目 | 结果 |
| --- | --- |
| 同一采购单品、搜索返回、报价详情、审核状态、个人/公司列表中同一记录 | 员工/管理员 JSON 字段全等；权限决定可见范围和操作，不另算金额 |
| 同一报价详情展示 | 组件测试逐字比较公共详情数据相同；员工没有审核按钮，管理员有；两端共享审核结论 |
| 同 SKU 同时粘贴 | 最终仅一条，未覆盖原值；并发冲突方可能收到 409，重试后跳过。普通顺序重试返回新增0条 |
| 无效整批/101行超限 | 422，未部分写入；合法上限100行整批可查 |
| 多管理员争抢同一报价 | 仅一个成功，其余409；过期版本不能完成审核 |
| 员工越权粘贴/审核/其他人审核状态 | 写入403；其他员工记录不泄露 |
| 审核与客户改价同时发生 | PostgreSQL 验证不会留下未核对的新价格已审核；备注/成交变更沿用原业务规则 |
| 审核与归档、回收站 | PostgreSQL 验证竞争不能同时错误成功，恢复不复活审核占用 |
| 审核筛选为空→有数据、记录离开筛选、慢列表请求 | 自动更新数量和列表，无重复轮询重叠 |
| 断网、超时、隐藏页面、重新联网、切换账号/分页、乱序旧响应 | 保留最后已知状态并提示失败，恢复重试，旧响应不覆盖新账号/版本，卸载取消请求 |
| 草稿恢复、采购阶梯、单品/组合成本、重新发起、财务初始化 | 聚焦前端回归通过；缺product旧草稿额外修复并实页复验 |
| 财务、物流、既有采购、报价正文与草稿 | 正常压力前后及浏览器验收后指纹全等（审核记录在独立审核表中变化） |

逐库核验 `LD-<run>-*`：50阶段 count/distinct SKU/正确价格重量且可报价均为41,620；100阶段三项均为63,010。历史保护指纹覆盖5项财务设置、1物流版本、1渠道、10,000既有采购、2,600报价正文及60草稿。

前端先完成16文件153项联动回归；后续最终审核/同步2文件22项、草稿/采购/重新发起/财务初始化4文件28项通过，计数有重叠，不相加。后端专项6类最终汇总30项通过，其中PostgreSQL审核12项包含返回版本的新回归；类型检查、针对修改文件的lint和diff检查通过。
