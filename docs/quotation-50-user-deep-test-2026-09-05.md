宿主：Windows、Ryzen 5 5600GT、6核12线程、约16GB内存。50名虚拟用户保持独立会话，每个逻辑操作完成后等待250毫秒，再继续操作。物流加载包含manifest及规则两个顺序请求；保存和读回也包含多个请求。这是持续密集使用，不等于50人仅保持登录。

每轮预热60秒、测量600秒。资源采样每10秒一次。原始证据位于被Git忽略的 `artifacts/performance/`，汇总见 [完整指标](performance/quotation-50-user-deep-results.json)。这仍不是数小时或数天的稳定性证明。

50并发由50个独立认证HTTP会话产生，不是同时启动50个完整浏览器。前端交互另用单个登录浏览器测量，因此报告分别列出服务端容量和页面操作证据。

## 采购查询原因与参数边界

原查询同时匹配SKU和完整JSON资料。已有两个GIN三元组索引，但新增资料会积累GIN待处理条目，使优化器估计索引路径更昂贵，转而扫描整表。

隔离执行计划证据：此前选择Seq Scan；维护后选择两个索引的BitmapOr。维护后示例查询耗时约18.57ms，维护前的示例处于并发负载下，不能直接据此计算性能倍数。持续负载复测才是验收依据。未改变搜索覆盖字段、匹配语义，也没有通过减少结果来制造加速。

测试参数只用于现有索引，未新增接口或迁移。降低待处理区阈值会让索引清理更频繁，可能增加批量导入写入开销；本轮覆盖持续逐条新增，未重新测量大型Excel批量导入吞吐。生产采用前需审核这项取舍。

生产只读核对：当前251条采购资料，两个搜索索引无自定义参数；服务器4 CPU、约7.1GiB内存，报价与其他服务共享主机。不能把全部主机资源视为报价独占，不能将隔离50人指标直接称作生产50人指标。

发现并处理的具体问题：

1. `financeAllowsLogisticsChannel`原本每判断一个渠道都会生成、描述澳大利亚区域并排序完整渠道列表；改为使用已有规则ID索引直接校验资格。174条真实形状规则、467种国家名称/代码，共81258次资格比对，0差异。旧组件实验把财务授权设为恒真，未覆盖这段实际成本，故其0.48ms结果不能解释完整页面表现。
2. 澳大利亚区域名称先规范化再去重，避免“1区”和“澳大利亚1区”显示为两个相同选项。
3. 草稿在冷启动时不再用尚未加载的物流规则筛掉区域；加载完成后再校验。全新页面恢复澳大利亚4区、38条渠道和无关税成功。
4. 采购搜索增加请求代次隔离，在新输入的250ms等待期间就使旧结果失效；旧请求最后成功或失败也不能改写新结果、提示或加载状态。可控乱序测试在修复前失败、修复后通过。空筛选状态下重置分页也会重新读取第一页。
5. 财务初次加载503后，重试虽成功，页面仍可能使用初始化时的默认汇率6.75。改为在财务配置成功加载后、草稿重新计算前同步汇率和客户等级；浏览器复测正确恢复实际汇率7。读取异常提示同时修正为“报价工作区读取失败”，避免误导为草稿写入失败。

三种报价模式切换后已选渠道保留。隔离浏览器成功保存澳大利亚报价，数据库快照为 `quoteRegion=澳大利亚4区`、`taxFeeMode=no-tax`、`taxLabel=无关税`。采购界面新增商品读回采购价12.5、重量120g成功。没有创建生产测试报价。

## 50并发异常测试

17组各50请求，共850次异常/竞争请求，加1项顺序幂等重放核对，全部通过。异常请求与正常持续负载分开统计，不将预期的401/403/409/422算作正常压测失败。

- 未登录读取401；不存在商品404；缺少CSRF写入403。
- 业务员修改财务/采购403，采购访问物流管理403，他人报价修改403。
- 负价格与无效报价422；过期物流版本409；篡改运费409。
- 同版本采购编辑、财务编辑、草稿编辑：各1次成功、49次409，未覆盖较新数据。
- 同一幂等键同时提交50次报价：50次均返回同一记录ID；再次重放仍为同一记录；同键不同内容409。
- 同物流商编码并发新增：1次成功、49次409。

隔离浏览器另做两类503故障注入：财务加载失败时明确报错、保存不可用，恢复接口并重试后汇率7且草稿按当前规则重算；物流manifest与规则接口同时失败时显示“已使用缓存物流规则，仅可查看；联网确认版本后才能保存”，保存禁用。恢复接口并重新查询后，澳大利亚4区仍可用，加入渠道后保存按钮重新启用。只让规则接口失败而manifest仍能验证版本时，已验证本地规则缓存可正常复用。所有故障配置已恢复为原始Nginx配置。
